# 문제를 어떻게 풀었나

이 프로젝트에서 가장 어려웠던 문제는 펫 UI가 아니라 **"이 펫의 세션은 지금 어느 Windows Terminal 창에 있는가"**였다. 이 문서는 그 문제를 두고 무엇을 시도했고, 왜 버렸고, 무엇을 남겼는지를 시간 순서로 정리한다. 세부 설계와 측정값은 각 절에 링크한 원문에 있다.

## 1. 문제: 세션과 창을 잇는 공식 경로가 없다

펫을 Ctrl+클릭하면 그 세션이 실행 중인 Windows Terminal 창을 앞으로 가져와야 한다. 그런데 Windows Terminal은 "이 프로세스가 어느 창의 어느 탭에 있는가"를 알려주는 API를 제공하지 않는다. Win32로 다룰 수 있는 것은 top-level 창 handle까지이고, 탭은 창 내부의 UI 요소일 뿐이다.

여기에 사용자가 탭을 한 창으로 합치거나(merge) 다시 떼어내면(split) 세션이 들어 있는 창 자체가 바뀐다. 펫은 그 변화를 직접 알 방법이 없다.

## 2. 첫 접근: 창을 상시 추적한다

처음에는 펫이 2초마다 owner 창을 다시 확인하는 방식으로 이 공백을 메웠다. 창 목록이 바뀌었는지, 다른 펫이 owner-map을 갱신했는지 감시하고, 바뀌면 owner를 다시 해석했다.

해석에 쓰는 근거는 처음엔 넓었다. foreground 창, 화면상 창 순서, 같은 프로세스의 창 같은 추정 근거도 썼는데, 탭 병합·분리 뒤에 **다른 세션의 창으로 포커스가 가는 오포커싱**이 생겼다. 그래서 owner를 확정할 때는 검증 가능한 근거(trusted)만 쓰기로 바꿨다.

- session marker: 세션의 콘솔 제목을 잠깐 고유 문자열로 바꾼 뒤, 그 제목을 가진 창을 찾는다.
- owner-map: 이전에 검증된 세션↔창 기록.
- tab title: hook 시점에 캡처한 탭 제목과 창 제목의 일치.

추정 근거는 owner 확정에 쓰지 않는다. **owner를 모르면 임의의 창을 잡지 않고 모르는 채로 둔다**는 원칙도 이때 생겼다. 틀린 창을 띄우는 것보다 연결이 끊겼다고 알리는(`disconnected`) 쪽이 낫다는 판단이다.

## 3. 추적 자체가 문제를 만들고 있었다

trusted 근거만 쓰도록 바꾼 뒤에도 병합·분리 직후 불안정이 남았다. 창 분리 시나리오를 실제 펫으로 재현해 transition log를 분석하자 원인이 드러났다.

- **자기 유발 루프.** 펫이 owner-map에 자기 기록을 쓴 직후 그 변경을 다음 tick에 "외부 변경"으로 다시 감지했다. 창이 바뀐 뒤 약 6초간 재검증과 재해석이 반복됐다.
- **탭 제목 깜빡임.** 재검증마다 session marker probe가 실행되어, 사용자 눈에 탭 제목이 marker 문자열로 수차례 깜빡였다. 병합(shared owner) 상태를 재현한 환경에서는 아무 조작이 없어도 10.2초마다 이 사이클이 돌았다.
- **복잡도.** 당시 `pet.ps1` 함수 83개 중 34개(41%)가 owner 추적용이었다. 프로젝트의 목적은 "터미널을 보지 않고도 상태를 한눈에"인데, 코드의 무게중심은 추적 상태기계에 있었다.

자기 기록 직후 감시 기준값을 갱신하는 한 줄 수정(P1)으로 루프는 막았다. 하지만 이것은 가교일 뿐, 근본 원인은 따로 있다고 판단했다. **공식 API가 없는 정보를 상시 추적으로 메우려 하면, 추적 자체가 경합을 만든다.**

## 4. 질문을 바꿨다: owner가 정확해야 하는 순간은 언제인가

다시 처음 기획으로 돌아가 보니, owner 창이 정확해야 하는 순간은 **사용자가 펫을 클릭해 창을 가져올 때뿐**이었다. 상태 표시에는 owner가 필요 없다. 상태 정의(`STATES.md`)도 `disconnected`를 "창 가져오기에 실패했을 때"로 정의하고 있었다.

그래서 상시 추적을 폐기하고 **클릭하는 순간에만 owner를 해석**하도록 바꿨다(P2). 클릭 시점 해석 경로는 이미 있었으므로, 새로 만든 것이 아니라 타이머의 추적 기능을 걷어낸 작업이었다. 타이머에는 세션 종료 감지 같은 생명주기 기능만 남겼다.

- 결과: 약 470줄 삭제. 같은 합성 환경에서 안정 상태 로그가 10.2초마다 5줄에서 0줄이 됐고, 새 창을 열어도 아무 재검증이 일어나지 않았다.
- 변화한 점: 창이 사라져도 펫은 다음 클릭 전까지 마지막 상태를 유지한다. 미리 `disconnected`를 띄우지 않는다. 사용자에게 필요한 것은 "클릭하면 맞는 창이 온다"이고, 그 동작은 그대로다.

원문: [design-2026-07-07-p2-click-time-owner.md](design-2026-07-07-p2-click-time-owner.md)

## 5. 남은 침습을 없앴다: 쓰지 않고 읽는다

P2로 session marker probe는 클릭 시점에만 실행되게 됐지만, 여전히 콘솔 제목을 바꾸는 침습적인 방법이었다. 클릭할 때 탭 제목이 깜빡이고, 재시도 대기 때문에 최대 약 1.5초 펫이 멈췄다.

핵심은 기존 tab title 매칭이 왜 부족했는지에 있었다. 창 제목(`GetWindowText`)은 **활성 탭의 제목만** 반영한다. 병합된 창에서 내 세션 탭이 비활성이면 찾을 수 없었고, 그래서 marker probe가 필요했다. 반면 UI Automation으로 Windows Terminal의 tab strip을 읽으면 **비활성 탭 이름까지 모두** 보인다.

그래서 tab strip 열거를 trusted 해석의 1순위로 두고(P3), marker probe는 실패할 때의 fallback으로 남겼다.

- 쓰기가 없으므로 깜빡임이 없다. 실측 창당 8~26ms.
- 매칭 탭을 가진 창이 **정확히 1개일 때만** 성공으로 본다. 0개나 여러 개면 다음 근거로 넘어간다. 추정으로 확정하지 않는다는 원칙은 그대로다.
- 비활성 탭 + 다른 제목의 활성 탭으로 구성한, 창 제목 매칭으로는 불가능한 배치에서 marker probe 없이 올바른 창을 찾는 것을 확인했다.

원문: [design-2026-07-08-p3-uia-tab-strip.md](design-2026-07-08-p3-uia-tab-strip.md)

## 6. 하지 않기로 한 것

풀 수 있어도 하지 않은 것들이 있다. 범위를 지키는 것도 설계의 일부로 봤다.

- **탭 내부 선택.** 창을 가져온 뒤 그 탭까지 선택하려면 Windows Terminal 내부 UI를 조작해야 한다. wrapper로 탭 제목을 고정하는 실험에서 Claude 입력이 불안정해졌고, 탭 제목은 Claude나 셸이 바꿀 수 있으며, UI 트리는 버전마다 다를 수 있다. 실패 지점이 기본 기능보다 많아서 보류했다. 병합 상태에서는 "그 세션이 들어 있는 창을 앞으로"까지가 정상 동작이다. → [TAB-MOVEMENT-NOTES.md](../TAB-MOVEMENT-NOTES.md)
- **펫 등장 지연 해소.** `claude` 실행 후 펫이 처음 보이기까지 콜드 기준 약 7초가 걸린다. 구간별로 측정해 보니 대부분이 세션마다 새 PowerShell과 WPF를 띄우는 비용이었다. 펫 프로세스를 상시 살려 두는 구조로 바꾸면 없앨 수 있지만, "세션당 펫 1개, 세션이 끝나면 정리" 원칙과 충돌하고 상시 메모리를 쓴다. 측정 결과를 기록으로 남기고 현재 구조의 바닥값으로 수용했다. → [diagnosis-2026-08-19-pet-launch-latency.md](diagnosis-2026-08-19-pet-launch-latency.md)
- **다른 언어로 재작성.** 복잡도가 높았을 때 .NET 단일 프로그램으로 다시 쓰는 안도 검토했다. P2로 코드가 줄면 재작성의 근거 자체가 약해진다고 보고 보류했다.

## 7. 남은 원칙

이 과정을 거쳐 남은 규칙은 [CLAUDE.md](../CLAUDE.md)와 [feature-spec.md](feature-spec.md) §7에 있다. 요약하면 다음과 같다.

- owner는 검증 가능한 근거로만 확정한다. 모르면 임의의 창을 잡지 않는다.
- owner 해석은 필요한 순간(클릭)에만 한다.
- 탭 병합 자체로 펫이 사라지거나 `disconnected`가 되면 안 된다. 병합 상태에서는 각 펫이 같은 창을 공유할 수 있다.
- 다룰 수 없는 영역(탭 내부 선택, 지원하지 않는 터미널)은 기능을 늘리지 않고 범위 밖으로 명시한다.
